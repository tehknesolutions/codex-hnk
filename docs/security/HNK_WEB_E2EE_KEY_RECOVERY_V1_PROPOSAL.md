# HNK Web E2EE Key & Recovery V1 — Proposal

**Status:** SECURITY DESIGN PROPOSAL · NOT ENABLED · APPROVAL / THREAT-REVIEW REQUIRED  
**Scope:** Web Vault interoperability with current Native Vault V1  
**Date:** 2026-09-03

This proposal defines a testable architecture for Web Vault key storage, recovery and multi-device enrollment. It does **not** authorize enabling Web Vault writes or Day 001 Web completion yet.

## 1. Security objective

A compromise of the HNK application database or Supabase service credentials must not, by itself, reveal plaintext Vault prose.

The server may persist:

- journal ciphertext;
- nonces / AAD / integrity metadata;
- encrypted key envelopes;
- public enrollment metadata;
- version / rotation metadata.

The server must not receive:

- plaintext journal prose;
- an unwrapped Vault Data Key;
- the user's Recovery Root Secret;
- a browser Device Key in extractable form.

## 2. Current Native contract that must be preserved

Native Vault V1 already uses:

- AES-256-GCM for entry encryption;
- a per-user AES key;
- device SecureStore / platform keychain;
- device-only keychain accessibility semantics;
- ciphertext-only persistence through `saveEncryptedVaultEntry()`.

The existing Native key can be encoded by the native crypto implementation. Therefore a future migration can wrap the existing 256-bit Vault key rather than re-encrypt every historical journal entry.

No migration is executed by this proposal.

## 3. Proposed key hierarchy

```text
Recovery Root Secret (RRS)
  user-held, random, high entropy, never uploaded
        |
        | HKDF-SHA-256
        v
Recovery Key Encryption Key (RKEK)
        |
        | wraps
        v
Vault Data Key (VDK) -----------------------> AES-256-GCM journal encryption
        |
        | locally wrapped by
        v
Device Key Encryption Key (DKEK)
  non-extractable CryptoKey stored in IndexedDB
```

### Vault Data Key — VDK

- 256-bit symmetric key;
- cryptographic identity of one Vault key version;
- used for AES-256-GCM entry encryption/decryption;
- may originate from the existing Native V1 key during migration;
- never stored unwrapped in Supabase;
- imported as a non-extractable working `CryptoKey` after recovery/enrollment where possible.

### Recovery Root Secret — RRS

- generated client-side from cryptographically secure random bytes;
- minimum proposal: 256 bits of entropy;
- encoded for human backup using a deterministic representation to be selected separately;
- shown to the user only through explicit recovery setup;
- never reused as the HNK login password;
- never transmitted to Supabase, analytics, logs or telemetry.

The baseline proposal deliberately prefers a generated high-entropy recovery secret over a memorable password. This removes dependence on an offline-guessable low-entropy password for the primary recovery envelope.

### Recovery KEK — RKEK

Derived locally using HKDF-SHA-256 from the RRS with versioned context, for example:

```text
salt = random per-vault salt stored with envelope metadata
info = "hnk-vault-recovery-v1:<user-id>:<key-version>"
output = 256-bit wrapping key
```

The exact binary encoding must be frozen in test vectors before release.

### Device KEK — DKEK

- generated by Web Crypto on the enrolled browser;
- non-extractable;
- usage limited to key wrapping/unwrapping;
- persisted as a `CryptoKey` object in IndexedDB;
- never serialized as raw key material by application code.

Losing/clearing browser storage destroys that device enrollment but does not destroy the Vault if the user retains the RRS or another approved enrolled device.

## 4. Key envelopes

### Recovery envelope — server-stored

The VDK is wrapped by the RKEK. Supabase stores only the wrapped VDK and non-secret metadata.

Proposed envelope metadata:

```text
schema = hnk-vault-key-envelope-v1
user_id
key_version
envelope_kind = recovery
wrap_alg = AES-KW-256 or approved AEAD wrapping profile
kdf_alg = HKDF-SHA-256
kdf_salt
kdf_info_version
wrapped_vdk
created_at
rotated_at nullable
revoked_at nullable
```

Final wrap algorithm choice must be locked by cross-browser test vectors before schema migration.

### Device envelope — browser-local

The same VDK is wrapped by the browser DKEK and stored in IndexedDB beside non-secret metadata.

```text
schema = hnk-vault-device-envelope-v1
key_version
device_id
wrapped_vdk
wrap_alg
created_at
```

The DKEK itself remains a non-extractable `CryptoKey` object in IndexedDB.

## 5. First Web enrollment

A user with an existing Native Vault should not receive a new unrelated Web Vault key.

Proposed migration path:

1. Native app authenticates normally.
2. Native app loads its existing V1 Vault key from SecureStore.
3. User explicitly starts `Enable encrypted Web recovery`.
4. Client generates RRS locally.
5. Client derives RKEK locally.
6. Existing Native VDK is wrapped into the Recovery envelope.
7. Only the wrapped envelope is uploaded.
8. User confirms recovery material backup.
9. Web device can subsequently enroll by supplying the RRS.

If the Native key is not available, the migration must not silently create a second key for historical entries.

## 6. New Web-only enrollment

If a future user has no existing Vault:

1. generate VDK client-side;
2. generate RRS client-side;
3. derive RKEK;
4. create Recovery envelope;
5. generate non-extractable DKEK;
6. create local Device envelope;
7. store DKEK + Device envelope in IndexedDB;
8. upload Recovery envelope only after user confirms recovery setup;
9. enable Vault writes only after a local decrypt self-test succeeds.

## 7. Recovery on a new browser

1. authenticate HNK account;
2. download Recovery envelope;
3. user supplies RRS locally;
4. derive RKEK locally;
5. unwrap VDK locally;
6. decrypt a versioned key-check value, not private journal prose, to verify the key;
7. create new non-extractable DKEK;
8. wrap VDK into a new local Device envelope;
9. discard transient raw/unwrap material as early as the platform allows;
10. mark browser enrolled locally.

The RRS is never uploaded as a verification credential.

## 8. Optional WebAuthn PRF enhancement

WebAuthn PRF may later be used as an optional device-unlock or wrapping factor where capability detection succeeds.

Possible role:

```text
WebAuthn credential + PRF input
        |
        v
PRF output
        |
        | HKDF
        v
Authenticator-bound KEK
        |
        v
wrap / unwrap local VDK envelope
```

It is **not** the V1 portability baseline because PRF behavior/support remains browser/authenticator dependent and must be capability-tested at runtime.

No WebAuthn PRF output may become the sole recovery mechanism unless cross-device recovery semantics are separately proven.

## 9. Threat model

### Must protect against

- read-only Supabase/database compromise;
- leaked service-role/database dump without user recovery material;
- stolen journal ciphertext;
- stolen Recovery envelope;
- attacker who knows the HNK account password but does not possess an unlocked enrolled device or RRS;
- browser storage loss;
- loss of one enrolled device.

### Cannot fully protect against

A Web E2EE application cannot guarantee secrecy against an attacker who can actively serve/execute malicious JavaScript from the trusted HNK origin at the moment the user unlocks the Vault.

Therefore release hardening must also include:

- strict CSP;
- dependency / supply-chain controls;
- no untrusted third-party scripts on Vault surfaces;
- production origin discipline;
- XSS prevention / sanitization;
- release integrity monitoring;
- no private prose in analytics/error telemetry.

E2EE does not replace origin security.

## 10. Proposed database addition

Do not alter `journal_vault` to contain key material.

A separate table is recommended only after review:

`vault_key_envelopes`

Minimum conceptual fields:

```text
id
user_id
key_version
envelope_kind
wrapped_key
wrap_alg
kdf_alg nullable
kdf_salt nullable
kdf_info_version nullable
created_at
rotated_at nullable
revoked_at nullable
```

RLS must limit all rows to `auth.uid() = user_id`.

No plaintext recovery secret or unwrapped VDK column is permitted.

## 11. Rotation

Rotation must be explicit and versioned.

Two distinct operations must not be conflated:

### Recovery-envelope rotation

Change RRS/RKEK while keeping the same VDK.

- historical entry ciphertext does not change;
- create new Recovery envelope;
- validate recovery;
- revoke previous envelope.

### Data-key rotation

Create a new VDK version.

- new entries use new VDK;
- old entries remain tied to old key version unless explicitly re-encrypted;
- all required historical VDK envelopes must remain recoverable until migration completes.

## 12. Revocation

A browser Device envelope is primarily local. Revoking a server session does not erase an already unlocked local key from memory.

Product semantics must distinguish:

- Auth session revocation;
- local device enrollment deletion;
- Recovery envelope revocation;
- VDK rotation.

A remote server cannot prove deletion of secret material from an offline compromised device.

## 13. Unsupported-browser behavior

Web Vault remains unavailable when required primitives cannot be established.

Required baseline capabilities before enabling writes:

- secure context / HTTPS;
- `crypto.subtle`;
- AES-GCM;
- HKDF;
- approved wrapping primitive;
- IndexedDB persistence of required objects;
- successful non-extractable-key round-trip self-test.

Failure means:

`VAULT WEB UNAVAILABLE — CONTINUE ON MOBILE`

Never downgrade to plaintext, reversible obfuscation or a raw key in localStorage.

## 14. Executable acceptance suite required before enablement

### Crypto vectors

- deterministic HKDF test vector;
- VDK wrap/unwrap vector;
- AES-256-GCM entry encrypt/decrypt vector;
- AAD mismatch rejection;
- ciphertext/tag tamper rejection;
- wrong RRS rejection;
- wrong user/key-version context rejection.

### Browser storage

- DKEK is `extractable=false`;
- exporting DKEK fails;
- DKEK round-trip through IndexedDB succeeds;
- clearing IndexedDB makes local envelope unusable;
- recovery flow restores access with RRS;
- no Vault raw key appears in localStorage/sessionStorage.

### Server-compromise simulation

Given only:

- full `journal_vault` dump;
- full `vault_key_envelopes` dump;
- public application code;
- Supabase service credentials;

acceptance test must demonstrate that plaintext journal fixture cannot be recovered without RRS or an enrolled local key.

### Multi-device

- Device A creates/enrolls Vault;
- Device B authenticates but cannot decrypt before recovery;
- Device B recovers with RRS;
- both decrypt identical historical fixture;
- revoking Auth does not falsely claim cryptographic deletion;
- explicit local enrollment deletion removes Device B access until recovery.

### Native interoperability

- wrap an actual Native-compatible 256-bit VDK;
- Web recovers same VDK;
- Web decrypts an entry generated with the frozen Native AES-GCM payload format, or a versioned migration adapter proves compatibility;
- Native decrypts a Web-generated compatible fixture when the same VDK/version is used.

## 15. Release gates

Web `saveEncryptedVaultEntry()` remains prohibited until all are true:

1. proposal approved into an executable spec;
2. wrap format frozen with test vectors;
3. recovery UX approved;
4. schema migration reviewed;
5. IndexedDB / non-extractable key tests green on supported browsers;
6. server-compromise fixture test green;
7. Native interoperability test green;
8. CSP/origin hardening reviewed;
9. hosted HTTPS deployment exists;
10. hosted smoke proves no plaintext private prose or raw Vault key reaches server/logs.

Only after these gates may Web Day 001 enable:

`Vault write → Practice Record → completeCodexDay → +150 XP → server-confirmed first spark`.

## 16. External standards basis reviewed

The proposal is based on current platform capabilities documented by:

- Web Cryptography API / `CryptoKey`;
- `SubtleCrypto.deriveKey()` / HKDF;
- `SubtleCrypto.wrapKey()` / `unwrapKey()`;
- IndexedDB structured-clone storage of serializable `CryptoKey` objects;
- Web Authentication Level 3 PRF extension as an optional enhancement.

Browser/authenticator capability must still be detected at runtime; standards availability is not equivalent to a universal secure-keystore guarantee.
