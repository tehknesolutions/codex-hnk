## 3. HNK-KODE developments

### Mandala numeric architecture

Current structural model:

- 432 MF = 72 sectors x 6 layers = generative Glyph Field.
- 463 ACTIVE = 432 MF + 9 external + 22 center = canonical Code Space candidate.
- 504 physical slots = 463 active + 41 reserved.
- HNK40 remains a genesis/validation corpus, not a declaration that the Mandala has only 40 units.
- 12 fundamental HENUVOKODAN keys/letters remain the phonological/symbolic foundation.
- Glyphs can be PATHs over addresses rather than one glyph = one cell.

Core form:

GLYPH = START_CELL + PATH + EDGE_SEQUENCE + TRANSFORM

### Glyph Genesis / E5 research

Research has moved toward exact combinatorial measurement and pruning rather than numerological guessing. Raw structural walks are explicitly not equal to unique usable glyphs; the pipeline must distinguish raw walks, simple paths, geometric equivalences, visually distinct glyphs and linguistically usable capacity.

### Computational language

HNK-KODE Programming Language/KODESCRIPT is now a first-class project. Minimal execution target:

KODE SOURCE -> AST -> HNK-IR -> RUNTIME WORLD

Initial declaration surface:

world -> entity -> property -> event -> action

Longer-term scope may include World, Game, UI, Backend, Data, Network, AI and Automation, but the minimal executable language must be proven first.

### Mandala-HNK Computational Model (MHCM)

Direction frozen:

Mandala-HNK = Encoding + Grammar + Computational Substrate

Target invariant:

TEXT <-> AST <-> MANDALA <-> GLYPH <-> HNK-IR

The Mandala may participate in addressing, composition, transforms, types, relations, PATHs and execution only where semantics are formally specified. No arbitrary assignment of opcodes/types merely to fill 432/463/504 positions.

Next architecture artifact: MHCM v0.1 defining Cell, Address, Path, Edge, Glyph, Transform, Composition, Type, Operator, Program and Mandala <-> AST <-> HNK-IR rules.
